# 프롬프트 설계서: 축구 선수 포커싱 웹앱

## 1. 목표

- 최종 목표: 축구 경기 영상을 실시간으로 보면서 원하는 선수 한 명을 따라가는 화면을 제공한다.
- 첫 버전(MVP): 사용자가 업로드한 축구 경기 영상에서 선수를 선택하면, 재생 화면이 그 선수를 따라 확대·이동하는 웹앱을 만든다. 이번 요청에서는 앱을 구현하지 않고 구현 계획만 작성한다.

## 2. 맥락

- 사용자는 좋아하는 선수나 직접 경기에 뛴 자신을 중심으로 경기 영상을 다시 보고 싶다.
- 사용 흐름은 축구 영상 업로드 → 영상 분석 → 화면 속 선수 선택 → 선택한 선수를 따라가는 확대 화면 재생이다.
- 선수는 이름이나 얼굴로 식별하지 않는다. 사용자가 영상 속 대상을 직접 선택하고, 앱은 그 대상의 화면상 위치를 시간에 따라 추적한다.
- 영상은 우선 업로드 파일을 사용한다. 실시간 송출 및 실시간 영상 분석은 이후 단계다.
- 대상 기기, 지원 영상 형식·길이, 최대 업로드 크기, 영상 보관 기간은 아직 정해지지 않았다. 계획에서 권장 기본값과 그 이유를 제시한다.

## 3. 제약

- 지금은 계획만 작성한다. 앱 코드, 프로젝트 파일, 예시 영상은 만들지 않는다.
- 권장 기술 스택은 React + TypeScript + Vite(재생·선수 선택 화면), Python + FastAPI(영상 업로드·분석 상태·결과 API), OpenCV + Ultralytics YOLO/ByteTrack(사람 검출·프레임 간 추적)이다. 영상 파일은 로컬 디스크, 분석 상태와 위치 기록은 SQLite에 저장하는 구성을 우선 검토한다.
- 영상 분석은 요청 한 번에 오래 걸릴 수 있으므로 API 응답과 분리한 작업 프로세스에서 실행하는 방안을 계획에 포함한다.
- 포커싱은 선택한 선수의 화면상 위치를 중심으로 재생 화면을 확대·이동하는 뜻이다. 확대 영역이 원본 영상 밖으로 벗어나지 않도록 처리한다. 영상 파일 자체를 편집하거나 내보내는 기능은 MVP 범위가 아니다.
- 사람 검출 결과에는 심판이나 관중이 섞일 수 있다. 선수가 가려지거나 카메라가 전환되면 추적 ID가 끊기거나 바뀔 수 있으므로, 포커싱이 불가능한 구간의 표시와 다시 선택하는 방법을 계획한다.
- 영상만으로 선수의 실명, 실제 이동 거리, 득점·패스 같은 경기 기록을 확정하지 않는다. MVP의 기록은 재생 시각과 화면상 위치·추적 상태로 한정한다.
- 외부 전송 없이 로컬에서 분석하는 구성을 우선한다. Ultralytics의 AGPL-3.0/Enterprise 사용 조건은 배포 방식이 정해지면 확인한다.

## 4. 출력 형식

다음 순서로 한국어 계획을 작성한다.

1. 만들 파일 목록과 파일마다 맡을 역할을 한 줄씩 적는다. 실제 파일은 만들지 않는다.
2. 화면에 보일 요소를 위에서 아래 순서로 적는다. 업로드, 분석 상태, 원본/포커싱 재생 화면, 선수 선택, 추적 실패 안내를 포함한다.
3. 영상 업로드부터 분석, 선수 선택, 확대 화면 갱신까지 데이터가 어떻게 흐르는지 설명한다.
4. 완료 기준의 각 항목을 어떤 영상과 동작으로 확인할지 하나씩 적는다.
5. 미정인 영상 조건과 배포 방식은 권장 기본값 또는 사용자에게 확인할 질문으로 구분한다.

## 5. 완료 기준

1. 축구 영상을 업로드하고 분석을 시작할 수 있다. 확인: 지원 형식의 짧은 축구 영상으로 업로드와 분석 시작을 시험한다.
2. 분석 진행·완료·실패 상태를 확인할 수 있다. 확인: 정상 영상과 읽을 수 없는 파일을 각각 넣어 상태와 오류 메시지를 확인한다.
3. 원본 영상에서 추적된 선수 한 명을 선택할 수 있다. 확인: 여러 사람이 보이는 장면에서 한 명을 선택해 해당 대상이 표시되는지 확인한다.
4. 재생 중 확대 화면이 선택한 선수의 움직임을 따라간다. 확인: 선수가 화면 좌우로 이동하는 구간을 재생하며 확대 영역이 이동하고 영상 경계를 넘지 않는지 확인한다.
5. 추적이 끊기거나 장면이 전환되면 상태를 알 수 있고 선수를 다시 선택할 수 있다. 확인: 선수가 가려지거나 화면 밖으로 나가는 구간을 재생한다.
6. 사용자가 실제 분석 결과와 예시 표시를 구분할 수 있다. 확인: 실제 결과가 없는 상태에서 가짜 추적 결과가 표시되지 않는지 확인한다.

## 6. 모호한 요청 vs 구체적인 요청 비교

- 모호한 요청: “축구 영상에서 좋아하는 선수를 포커싱하는 앱을 만들어 줘.”
- 구체적인 요청: “축구 경기 영상을 업로드한 뒤 사용자가 화면 속 선수 한 명을 선택하면, 재생 화면이 그 선수를 따라 확대·이동하는 웹앱의 MVP 구현 계획을 작성해 줘. 실시간 송출은 이번 범위에서 제외해 줘. 선수를 놓치거나 카메라가 전환될 때의 안내와 재선택 방법을 포함해 줘. React·TypeScript·Vite, FastAPI, OpenCV와 YOLO/ByteTrack을 우선 검토하고, 만들 파일과 역할, 화면 요소의 위에서 아래 순서, 영상 처리 흐름, 완료 기준별 확인 방법을 순서대로 적어 줘. 파일은 만들지 말고 계획만 보여 줘. 결정이 필요한 사항이 있으면 계획 전에 질문해 줘.”

## 7. 무엇이 달라졌고 왜 달라졌나

- ‘포커싱’을 선수 주변으로 화면이 확대·이동하는 동작으로 정의했다. 단순히 선수에게 표시를 그리는 것과 구분된다.
- 실시간 송출이라는 최종 목표와 업로드 영상 분석이라는 MVP 범위를 나눴다. 이번에 계획할 기능이 명확해진다.
- 선수를 직접 선택하는 방법과 추적 실패 시 다시 선택하는 방법을 넣었다. 이름만으로 자동 식별하거나 추적이 항상 유지된다고 가정하지 않는다.
- 파일 역할, 화면 순서, 데이터 흐름, 항목별 확인 방법을 출력 형식에 명시했다. 계획을 보고 구현 범위와 검증 방법을 확인할 수 있다.
- 현재 요청이 계획 작성이라는 점을 명시했다. 계획 단계에서 앱 파일을 생성하지 않도록 한다.
